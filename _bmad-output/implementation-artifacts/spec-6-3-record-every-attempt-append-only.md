## Intent

**Problem:** The reducer counts hints and Harmful Moves per Lesson run, but nothing records the runs. A Learner's trend (FR-19, FR-20, SM-5) has no history, and repeated Lessons leave no trace (AD-10, AR-14, AR-21).

**Approach:** The reducer emits `Effect.AttemptStarted` when a Lesson run begins and `Effect.AttemptEnded(objectiveId, outcome, errors, hints, assistanceLevel)` when it ends. `SessionHost` turns each into an `AttemptRecord` keyed by `(sessionId, revision)`. It hands the records to the snapshot save of the same transition, which inserts them into a new append-only Room `attempt` table in the same transaction. A read port returns the log in insertion order.

## Boundaries & Constraints

**Always:**
- **Attempt.** An Attempt is one Lesson run toward the Lesson's Objective, with `objectiveId = lesson.id.value` (a Lesson has one Objective).
  - It **starts** on `LessonStarted` and on an applied `CheckpointRestored` (both give fresh tutor counters), but only when the new state's `objectiveMet` is false.
  - It **ends** once: the first Lesson transition after which `objectiveMet` is true while the attempt is open emits `AttemptEnded(COMPLETED)`. Any route counts (Move, Redo, Undo, *Try again*, Reset).
  - A `LessonStarted` that replaces a Lesson whose attempt is still open first emits `AttemptEnded(ABANDONED)` for the old attempt, with the old counters, then the new attempt's `AttemptStarted`.
  - Reset and *Try again* stay in the same attempt, because the counters are kept across them today. A `SessionRestored` continues the snapshotted attempt and emits nothing.
- **Fields.** `SessionState` gains two tutor fields, both of which never advance `revision`:
  - `attemptOpen: Boolean` — true from `AttemptStarted` until `AttemptEnded`.
  - `attemptAssistance: AssistanceLevel` — the highest `assistance` level shown during the open attempt, by enum order (`REDUCED < USUAL < EXPLAIN < DEMONSTRATE < GUIDE`). It is set to the `assistance` of the state where the attempt starts, then raised after every Lesson transition while the attempt is open, including the transition that ends it (raise first, then end).
  - IDLE and Solve Playback hold `false` and `USUAL`.
- **Effects.**
  - `AttemptStarted(effectId, revision, objectiveId, at)`.
  - `AttemptEnded(effectId, revision, objectiveId, outcome, errors, hints, assistanceLevel, at)`, where `outcome` is the new enum `AttemptOutcome { COMPLETED, ABANDONED }`, `errors = stepMistakes.values.sum()`, `hints = hintsUsed`, and `assistanceLevel = attemptAssistance`, all from the state that ends the attempt (for ABANDONED, the replaced state).
  - Each consumes one effect id. They are appended after the transition's existing effects in this order: `AttemptEnded`(ABANDONED), `PersistCheckpoint`, `AttemptStarted`, `AttemptEnded`(COMPLETED). Each carries the revision of the resulting state.
- **Records.** `AttemptRecord` (pure, in `:core:application/session`) holds:
  - `sessionId`, `revision`, `event` (`STARTED`/`ENDED`), `objectiveId`;
  - `outcome`, `errors`, `hints` and `assistanceLevel` (null for STARTED);
  - `at` (an `Instant`).
  - `AttemptRecord.of(effect, sessionId)` is pure.
- **Write.** In `dispatch`, `SessionHost` builds the transition's records with the host's `sessionId`, except that an ABANDONED row uses the `sessionId` from before the new session's id was generated. It passes them to `SessionSnapshotRepository.save(snapshot, attempts)` with that transition's snapshot.
- **Transaction.** `RoomSessionSnapshotRepository.save` inserts the records and writes the snapshot in one `withWriteTransaction`:
  - The records are inserted even when the snapshot is `Stale`.
  - Any exception rolls back both and returns `SnapshotSave.Failed`. The existing `SnapshotSaveFailed` event follows; there is no retry.
- **Storage.** Room schema v3 adds table `attempt`. Its columns are `seq` (autogenerated PK), `session_id`, `revision`, `event`, `objective_id`, nullable `outcome`, `errors`, `hints` and `assistance_level`, and `at_ms` (UTC epoch ms). It has a UNIQUE index on `(session_id, revision)`.
  - Rows are inserted with `OnConflictStrategy.IGNORE`, so a repeated key is a no-op. The DAO has no update, replace or delete.
  - The migration is `AutoMigration(2, 3)`, and the v3 schema is exported to `app/schemas/`.
- **Read.** The port `AttemptRepository.all()` returns `AttemptLoad.Found(records in seq order)` or `Failed`. Room exceptions become `Failed` (AD-12). It is bound in `PersistenceModule`.
- **Snapshot.** `SessionSnapshot` and `SnapshotPayload` carry `attemptOpen` and `attemptAssistance`.
  - The payload `format` stays 1. A payload without these fields decodes them as `false` and `USUAL`.
  - `SessionRestored` restores both fields.

**Never:**
- No row update, and no delete path or reset UI. Scoped resets are Epic 7. No Practice or 2-look attempts (Epic 7), no Mastery or trend UI, and no Continue card.
- No ViewModel or screen writes attempts. No Room, Android or serialization imports in `:core:*`, and no Cube States in attempt rows or logs.
- Never change the snapshot or checkpoint table schemas or the Checkpoint payload. Never edit planning artifacts, `_bmad/` or `.claude/skills/`.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Start | `LessonStarted` from IDLE | `PersistCheckpoint`, `AttemptStarted`; `attemptOpen` | — |
| Complete | The Move that meets the Objective | One `AttemptEnded(COMPLETED, errors, hints, level)`; `attemptOpen` false | — |
| Re-complete | Undo then Redo after completion | No second `AttemptEnded` | — |
| Abandon | `LessonStarted` (another Lesson) over an open attempt | ABANDONED (old counters, old sessionId) then STARTED, in one transaction with the new snapshot | — |
| Restore checkpoint | Applied `CheckpointRestored`, Objective not met | `AttemptStarted` | — |
| Restore snapshot | `SessionRestored` with an open attempt | No attempt effect; a later completion ends it | — |
| Replayed key | Same `(sessionId, revision)` inserted twice | The first row is kept unchanged | IGNORE |
| DB failure | The transaction throws | Neither the snapshot nor the rows are written; `SnapshotSaveFailed` | caught |

## Design Notes

- **Why STARTED and ENDED rows.** Rows are never updated, so an attempt is the pair of a STARTED row and the next ENDED row in `seq` order. There is at most one active session, and the single writer keeps commit order. A STARTED row with no ENDED row is an unfinished run, for example one lost to process death without a usable snapshot. That is the honest record, and nothing invents an end for it.
- **Key uniqueness.** A transition writes at most one row per session. The ABANDONED row belongs to the old session and uses that session's id with the new revision, which the old session never reached. So `(sessionId, revision)` is unique without a row-type column. `sessionId` is regenerated on every start and restore, and revisions restart after a restore, which is why the key needs both.
- **Abandoned runs.** A replaced open attempt still holds its counters, so it is closed as ABANDONED with them: hints and errors spent on a run the Learner gave up still count toward the trend. A run lost to process death without a snapshot has no counters left and stays STARTED-only.
- **Peak assistance.** AD-10 / M4 defines "reduced assistance" as a maximum `assistanceLevel` per attempt. Recording the most help shown lets Epic 7 compare it to that maximum.
