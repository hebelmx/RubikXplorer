# RubikXplorer sprint change proposal — record and replay continuous Quick Scan fixtures

**25 November 2026 · Draft for product-owner review · Planning only**

Keep the ability to record a failing scan and replay it offline when more evidence is needed. After the continuous Quick Scan pipeline is finished, migrate the developer recorder and its evaluation workflow to the same pipeline used by the app. Retire the old two-corner code only where that migration removes its last consumer.

## 1. Trigger and evidence

Story 10.23 (shadow sticker-reader comparison) used two distinct tools. The debug Android fixture recorder captures labelled examples. The offline Gradle task `exportKotlinStickerReads` reads those examples and calls `QuickScanClassification.report` and `.read` to produce the old baseline. Story 10.31 (continuous detector integration) already retired the shadow model and its Android hook. The capability to carry forward is capture and replay. [Recorder entry point](../../app/src/camera/debug/AndroidManifest.xml) · [Offline exporter](../../core/domain/src/evaluation/kotlin/dev/cubentia/domain/recognition/evaluation/sticker/KotlinStickerReads.kt) · [Story 10.23 evidence inventory](../../docs/evidence/10-23/inventory.md)

The recorder currently saves two prescribed holds per face. Its adb-triggered burst (`RecorderBurst`, Quick Scan reliability spike 2026-11-22) already writes consecutive frames to `frames.jsonl` with a JPEG every Nth frame, but each line is a two-corner reading and a `SideLight` check, not a continuous-detector observation. Neither path runs the continuous detector or mapper, so neither can reproduce the order in which faces appeared, a regrip or a conflict developing across frames. The burst's file layout and adb trigger are the natural starting point for the new capture.

Story 10.32 (live continuous Quick Scan) limits its cleanup to code not used by Case recognition or `FixtureRecorderActivity`. That protects the recorder screen, but not every legacy consumer: `exportKotlinStickerReads` (evaluation source set) calls `QuickScanClassification`, `RecorderBurst` calls `SideLight`, and the debug and release `ScanDiagnostics` reference Quick Scan types, all of which are on 10.32's removal list. **Handoff note for Story 10.32 (no acceptance change):** treat evaluation tasks, the burst and diagnostics as consumers too. Keep the class, or retire the caller only after recording the archived revision and command that reproduce its historical output. The change belongs in Epic 10 (camera recognition). The product requirement for continuous scanning and the learner experience already describe the desired pipeline. Architecture decision AD-9 (camera and frame handling) permits a debug-only fixture writer and prohibits persistence of learner frames in release and benchmark builds. The current debug exception describes a downscaled frame per face. The future story therefore needs an AD-9 amendment, drafted with the story and approved before implementation: allow an operator to retain a bounded sequence of cube frames in local debug storage so that a future detector can run against the same pixels. The writer belongs solely to the developer recorder. AD-9 also keeps raw frames and Android types out of `:core:domain`, which splits replay in two: state replay (recorded observations through a fresh mapper) runs in the `:core:domain` evaluation source set, while image replay through the LiteRT detector runs on the `:app` side (an instrumented debug test or an app-side JVM harness, chosen at scheduling). ## 3. Recommended approach

Schedule two deferred stories in Epic 10: **A**, continuous capture and offline replay (medium effort); **B**, retirement of verified dead code (small), which starts only after A's capture and replay demonstrations pass on a physical device. Splitting keeps a slow caller inventory from holding back the diagnostic tool. Replay fidelity and shared legacy callers are the main risks. Reverting pipeline work would reintroduce the fixed holds. Revising the product requirements would add scope without addressing either tool. Fixture collection beyond the examples needed to verify the migration is driven by a specific evidence gap.

## 4. Proposed backlog change

**Today:** the completed recorder, label checks and shadow-reader evaluation describe their original fixture formats. There is no post-pipeline story tying continuous capture, offline replay and retirement together.

**Proposed additions after the dependency check:** Story A, *Record and replay a continuous Quick Scan session in the developer fixture recorder*, takes the first five rows below. Story B, *Retire the legacy two-corner recorder and exporter paths*, takes the last row and depends on A. Assign the next available story numbers when scheduling. As a developer investigating a Quick Scan failure, I can deliberately record a scan while turning the cube, preserve the order of observations, and replay it against independently verified labels to reproduce where the result diverged.

| Acceptance | Demonstration |
| --- | --- |
| Use the app’s finished pipeline | Launch the existing debug recorder via its activity, start a session, turn the cube naturally, then stop or discard. Feed the same model, lattice fitter, sampler and stateful mapper used by the Solve-tab scan. Preserve Guided single-face fixture capture. With Case recognition disabled, continuous recording must work without loading the corner detector. |
| Produce a usable local fixture | A versioned group records the session ID, device, cube, lighting, model identity (file SHA-256) and build commit, frame order and timing, rotation/crop geometry, and sampled observations needed by the replay stage. For an image fixture, retain the ordered, bounded detector inputs with their preprocessing metadata so an updated model can be tested. Record any sampling or dropped frames. The story spec fixes the frame cap, stored resolution and per-session size budget. Only operator-curated groups are copied into `Fixtures/`, within a stated repository size budget. Preserve loss of tracking, empty observations and partial or failed sessions. Save to app-specific local storage only on operator request. An interrupted write cannot be mistaken for a complete group. Keep the writer out of release and benchmark artifacts. |
| Keep truth independent | Store operator-confirmed reference stickers separately from predicted colors, with unknowns explicit. Apply Story 10.28 (ground-truth quality checks) to a fully labelled group, including nine of each color and review provenance. A partial or deliberately invalid example stays available for diagnosis with an explicit outcome. Keep a capture session and its derivatives together in the chosen tuning or held-out partition. |
| Replay offline | Supply a documented replacement for the continuous use case of the old exporter. Replay ordered observations with a fresh mapper per session. State replay must be exact: the same observations yield the same net and cue sequence. For a known complete example, reproduce the recorded net in canonical face order and compare against operator truth. For a partial or failed example, reproduce its last confirmed net and cue or conflict without filling unknowns. For an image fixture, replay the saved inputs through the recorded detector version, check the detections against the captured baseline within a tolerance set in the story spec (on-device int8 and off-device runs can differ slightly), then run the same fixture with a candidate detector. Report the replay starting stage, observed coverage and label mismatches. |
| Preserve historical evidence | Existing `Fixtures/live` and `Fixtures/corner` examples, held-out membership, historical reports and labels remain readable as their original formats, and the tasks that read them (`evaluateScanAccuracy`, `evaluateMatrix`, the live baseline and `LiveFixture` decoding) keep running. Document the archived revision/command for reproducing legacy scores. Verify at least one old fixture and one new continuous group before retiring a legacy command. |
| Retire only proven dead code (Story B) | On the final merged pipeline, inventory Android, domain, evaluation, Gradle, fixture-decoder and test callers. Move each remaining consumer to its replacement or document its continuing owner. Remove or deprecate the old path only after the replacement capture and replay demonstrations pass. Verify Case recognition, Guided capture and old fixture decoding still pass. |

**Cleanup candidates to verify at execution.** The recorder uses `QuickScanPlan`, `SideLight` and two-corner capture helpers, and `RecorderBurst` uses `SideLight`. `exportKotlinStickerReads` uses `QuickScanClassification`. The debug and release `ScanDiagnostics` reference Quick Scan types. Audit the separate `evaluateQuickScan` measurement task on its own inputs before retiring it. Case capture uses `CornerHold`; the camera adapter also has shared `CornerLocator`, `CornerReader` and `CornerGuide` consumers. A disabled release flag is insufficient evidence of dead code. Use the post-pipeline tree for the actual deletion list. ## 5. Handoff and review

- **Product owner** reviews this proposal as planning. After the dependency gate, identify the first real capture need from the matrix or a reproducible failure and select a representative complete and incomplete example.
- **Developer** rechecks callers and the final pipeline interface, implements capture and replay together, and records the operator procedure, fixture format and historical replay instructions. Validate the debug recorder on a physical device, exercise the compatibility fixtures, and run the repository build and privacy/source-set checks before removing the last legacy dependency.
- **Architect** approves the AD-9 frames amendment and the replay placement before Story A starts.
- **Scope:** moderate, confined to developer tooling and its evaluation workflow. The proposed change to the backlog is two future stories and one AD-9 amendment. Operator instructions and format belong with the tooling when delivered. The learner PRD, learner UX and release settings require no edits. Story 10.32 needs only the handoff note in section 1, not an acceptance change.
